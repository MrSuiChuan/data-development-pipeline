# requirement-analysis

在 /submit 建单前使用：把自然语言需求翻译成机器可校验的工单。

## 输出模板（5 章）

```
## 背景      ——为什么做、现状痛点
## 目标      ——做到什么程度、产出什么
## 范围      ——目标表、来源表、不做什么
## 验收口径  ——数字可验证：字段口径、join_match_rate/null_rate 目标、用例数
## 风险      ——下游影响、回刷、口径冲突
```

同时补 8 项质量要素：主题【数据需求】开头、负责人、计划日期、来源声明。

## 判定难度级（给 P1 的 level_suggestion 做参考）

- L0：纯取数，不进研发管道（P1 即席出口）；
- L1：改造快线（改现有任务/加列/改值）；
- L2：待明确慢线（涉及中间层/多表）；
- L3：新建应用/长链路。

口径不明确是缺陷，不是“后面再说”：先问清或缩小范围，禁止含混建单。
