# 离线数开插件介绍

这是一个给数据研发用的插件，把数据仓库从接到需求到交付上线这一整条路，做成一个可以挂到 AI 宿主里的流水线。它能装在 Claude Code 上，也能装在 Codex 上，两边共用同一套引擎和同一套门禁。人在哪边工作，流程就在哪边跑。

它的定位可以用一句话说清。模型负责在门内干活，出门的时候按门的要求交出机器能验证的证据。

## 六个阶段和六道门

插件把研发过程拆成六个阶段，按 P1 到 P6 编号，每一段都有明确的交付物和放行条件，没到条件就停在那里，不会偷跑到下一段。

P1 是数据概要设计。产出是一份结构化的设计文件和一份 SQL 验证证据，字段口径逐条对过，来源表要真实可见。这一段的门有八条硬规则，例如目标表必须明确、字段映射要带验证证据、口径要给出结论。八条都过了才算完。

P2 是架构设计。产出是架构文档和交付表清单，其中清单是机器可读的。后面 P3 会拿这份清单和实际交付的表做集合比对，多写一张少写一张都会被打回。

P3 是数据研发。产出是三层文件，分别是建表、数据处理和调度任务，三层的表名集合必须一致。这段要过两关，一关是按引擎方言做的 SQL 检查，另一关是真实执行的记录。渲染出来的建表语句只是起始模板，照样要过检查，也要真跑。

P4 是数据测试。产出是测试报告和机器证据，报告里标了通过的用例，必须在测试账本里找到同名的成功记录，那条记录还要带真实的执行编号。报告和数据对不上，这一段过不去。

P5 是运维部署。产出是部署计划，计划里每一项都精确到表和操作类型。发布这一个动作需要用户给出明确的确认标记，热更新、停止、下线、取消部署各自有独立门禁，回滚也要单独的确认。

P6 是语义层更新。这一段必须由人先拍板，模型不能自己决定进入。拍板之后产出更新说明，交给知识库那边收口。

六个阶段之间只允许逐级前进，跳阶段会被直接拦下。需要回跳的时候要显式申明原因，留在记录里。

## 门认什么证据

每一阶段的出口都不看模型的话，只看机器证据。以 P3 为例，每次真实执行都会在执行账本里留下一条记录，里面有执行编号、执行时间、执行环境，还有那条 SQL 的哈希。出口门会拿账本里的哈希和当前工作目录下的文件比对，一致才放行。改过 SQL 却想复用旧回执，门会直接判证据失效，要求重新真跑。

证据还有一个保鲜期。过期之后，后面阶段会要求重新执行，例如把三十小时前的记录拿来过 P4，门会按保鲜期判定过期。

证据分级别。连平台命令行拿到服务端执行编号的，记服务端回执。走数据库直连或命令行客户端的，记本地回执。演示或模拟环境下产生的，记模拟回执。级别在报告里怎么写就怎么显示，不会把本地回执说成平台编号。

账本里有专门的命令可以自查与确认，分别是证据校验、证据自检和证据确认。手写的回执会在这里被拦住，理由也很直接，执行证据只能来自引擎自己的执行记录。

## 写之前就先拦住的那些门

除了阶段出口门，插件还有一层写前门禁，挂载在宿主的工具调用上。它会检查这次动作要写哪里、用的什么执行器、对象是不是已经定位清楚。往流水线运行目录里直写文件、绕过引擎去调平台命令、在没建单的情况下动业务对象，这几类动作都会在发生之前被拦下来。

这一层有个现实问题需要说清楚。宿主的钩子如果没有正确配置，失败的方式是静默放行而不是报错。所以插件带了一个适配脚本，非 Windows 环境装完之后要跑一次，把钩子里的启动器换成本机可用的解释器。检查命令会明确告诉你当前是否可用。

## 引擎和方言

数据平台是可插拔的，引擎清单只有一份权威文件，登记每个执行器的所属执行族、方言、必填配置项、默认端口和证据级别。执行族有四类，分别是数据库直连、命令行客户端、平台命令行契约和会话内通道。

目前登记的引擎有十九类。MySQL 协议族包括 MySQL、Doris、StarRocks、TiDB、OceanBase 和通用协议兼容库。命令行族包括 Hive、Spark SQL、Flink SQL、Trino、Presto、ClickHouse、PostgreSQL、Greenplum 和 MaxCompute。另外还有自定义命令行、平台命令行契约和预留的会话通道。

配置好之后先跑一次平台体检。它会逐项核对执行器是否登记、必填项是否齐全、多环境配置形状是否正确、有没有明文口令。未登记的执行器一律直接报错并列出可用项，不会退回默认通道。

写 SQL 的时候可以按引擎做方言检查，不指定方言时按当前执行器推导。检查规则里，像 Hive 上的更新删除、Trino 上的覆盖写、MaxCompute 上的行级写，这些是硬失败。Doris、StarRocks、Spark 和 PostgreSQL 上的条件性写法给警告并附修复建议。规则清单会跟着引擎版本演进，每个引擎都有一份真实执行留下的报告做背书。

建表语句由插件按引擎渲染，类型映射写在代码里，从统一类型到各个引擎的物理类型都有对照，例如 Doris 用 DECIMALV3，Hive 用 DECIMAL，ClickHouse 用 Decimal，PostgreSQL 用 NUMERIC。遇到未知类型或未知方言直接报错，渲染产物默认不覆盖已有文件，需要显式允许才会覆盖。

湖表格式是一个和执行引擎正交的维度，可以是 Iceberg、Hudi、Paimon、Delta 或者不使用。建表和检查都认这个维度，组合没有登记同样会被体检拦下。调度器也做成维度，可以选择定时表达式、Airflow、DolphinScheduler、DataWorks 或者不需要调度。

## 连接器

插件要打交道的四个外部系统都是可配置的。任务单系统用一份 JSON 命令行契约对接，数据平台用上一条说的引擎适配器，质量规则系统同样走命令行契约，知识库既支持命令行，也支持直连 OpenViking 的 HTTP 接口。

默认是模拟模式，不需要任何真实系统就能把六个阶段跑通一遍。切到真实模式之后，口令和密钥只从环境变量或本地密钥文件读取，不写进配置文件，也不会出现在产物里。

## 怎么用它

在 Claude Code 里，它提供九个斜杠命令，分别是初始化、建单、概要设计、启动流水线、单动作穿插、跨会话续接、阶段转场、看状态和查看全貌。在 Codex 里，对应的是九个同名技能，另外还有十五个方法论技能，覆盖需求拆解、概要设计、架构设计、研发、测试、部署、语义层，以及指标、特征、中间层、回刷、质量规则、域知识和会话复盘这些叠加场景。

上手路径很短。先初始化项目运行时，再用建单入口写一张数据需求工单，建单本身有八项质量检查，描述不清会直接被打回。之后可以一路跑完整条流水线，也可以只用单动作穿插，改一张表、补一个用例、查一下状态。

只想看看它长什么样，可以跑一次演示命令。它会自动把建单到语义层这六个阶段走完，包含全部门禁，全程不依赖任何真实组件，输出是确定性的。

## 产物长什么样

每个阶段的产物都落在工单目录下，有固定名字和固定结构。除了前面说的设计和测试文件，还有执行记录、部署计划、变更对比页和交付摘要。所有产物都能被后面的阶段读到，也能被独立审计。

插件还提供一份治理摘要命令，把时间线、证据、决策和未决项汇总成一份可交付的说明，需要时可以直接写成文件。

面向使用者的输出契约也做了统一。状态快查给对象、状态、观测时间和来源。巡检报告给关键发现、优先建议和依赖，并附取证记录和评分。诊断报告给现象、根因、链路和修复方案，结论分成已确认、较可能、已排除和未决四级。操作结果使用专用状态词，只会报告观察到的状态。

还有一组全局语义写进了文档，例如未发现不等于未安装，空列表不等于没有数据，查询失败不等于零事件，受理成功不等于生效，用户认可不等于证据。这几句话看着琐碎，实际就是日常最容易误判的地方。

## 边界

插件的仓库里带一份已知缺口清单，写得比功能列表还长。某些云服务组件无法在本地复现，单机验证覆盖不到集群形态的提交方式，命令行族的回执拿不到平台侧执行编号。这些都会在报告里如实标注，不会因为功能列表好看就省略。

许可证是 Apache 二点零。仓库里带了完整的发布流程、生成物一致性校验、分层纯度检查和真实执行报告。想要接一个自己的数据平台，改的是配置而不是代码；想要加一个引擎，改的是那一份权威清单。
