# 给 AI 修一条带门的跑道

去年到现在，我见过太多团队在同一个地方卡住。让模型写一段数仓 SQL，它往往几秒钟就给你一段看着挺像样的东西。真把它放到线上，问题就来了。字段口径对不对，上游表是不是已经发布，执行到底有没有跑过，跑了之后改过没有，发布的时候有没有人确认过。这些问题一个都不回答，那段 SQL 就只是一段文本。

我做这个离线数开插件，起因就是这件事。它管的东西很朴素，把数据研发这条流水线拆成六个阶段，每个阶段的出口装一道门，门只认机器能验证的证据。模型可以在门内自由发挥，出门的时候得拿东西来换。

## 六个阶段，六道门

六个阶段分别是数据概要设计、架构设计、数据研发、数据测试、运维部署和语义层更新，我按 P1 到 P6 编号。每一段都有一个明确的交付物，也都有一个明确的放行条件。

P1 的产出是概要和一份 SQL 验证证据，字段口径要一条条对过，来源表要真实可见。P2 出架构文档，其中交付表清单是机器可读的，后面 P3 会拿它和实际交付的表做集合比对，多写一张少写一张都过不去。P3 是研发这一步，三层文件 ddl、etl、dp_task 必须同名同序，SQL 要按引擎方言检查，还要有一次真实执行的记录。P4 要测试报告和机器证据，报告里标了通过的用例，必须能在 test_runs.json 里找到同名的成功记录，而且那条记录要带真实的 query_id。P5 是发布，需要数据库里那条部署计划的每一项都精确到表，并且带上用户明确给出的已确认发布标记。P6 走语义层，入口必须由人来拍板，模型不能自己决定进。

这些门不是装饰。我在真跑里抓到过一个典型例子。有一次流程走到 P5，部署命令返回了成功，结果清单却是空的。翻代码才发现，计划文件缺失的时候，它会拿着空计划一路走到底，什么都不发，还回一个成功，顺手把发布确认那一道门也跳过去了。这种情况在演示里看不出来，只有把整条链路真跑一遍才会露出来。后来加了一条硬拦，计划缺失或者清单为空就直接停。

我专门试过反向的路子，一共七条，全都被拦下来了。改完 SQL 想拿旧回执过关，门比对哈希之后直接判证据失效。把执行时间改成三十小时以前想蒙混过去，门按保鲜期判定过期，要求重新真跑。没拿到确认就想发布，发布门要那个确认标记。还有一次我手写了一条看着很像的回执，被账本门拦住了，理由写得很直白，执行证据只能来自引擎自己的执行记录，模型不能自己编。

## 为什么非要真跑

插件支持十九类执行引擎，从 MySQL 协议族到 Doris、StarRocks、ClickHouse、Trino、Hive、Spark，再到 Flink 加湖表。纸面上都支持，写进矩阵里也好看。我不太信纸面，所以这几个月里我把能本地装起来的都装起来跑了一遍。

Doris 用的是官方二进制包，三点九六个 G，单流下载速度会掉到每秒几 KB，最后改成八路分片才拉完。解包之后还有一堆环境上的硬要求，FE 只认 JDK 17，BE 在启动脚本里卡内存映射数，单 BE 集群建表默认副本数是三，直接失败。StarRocks 那边，官方 tar 在网络上拿不到，我用的是官方镜像，容器默认命令是 bash，直接后台运行会立刻退出，得让容器活着再进去起进程。

每一个引擎跑完都按同一个口径验收。渲染建表语句，真建表，写三行数据，读回来核对行数和金额，回执进执行账本，再过一遍证据校验，最后跑真实的阶段出口门。这个口径跑通的引擎现在有十几个，Doris 四点一点四、StarRocks 三点三点九、Flink 一点二十加 Paimon、TiDB、PrestoDB、Greenplum，还有 ClickHouse、Trino、Hive、Spark 和四种湖表格式。每一份现场都留下了报告，包括失败的和卡住的。

真跑的价值在于它会推翻你写好的模板。Doris 要求引擎子句写在键子句前面，反着写直接语法错。StarRocks 不认 BUCKETS AUTO 这种写法，那是 Doris 的口径。同一个字段类型映射，Doris 用 DECIMALV3，StarRocks 只认 DECIMAL。这些东西坐在办公室里推不出来，也不是多看几遍文档就能避免。

## 拿别人的仓库当考题

自己写的测试用例有个毛病，它总是干净的。为了知道脏数据长什么样，我找了那个开源电商数仓仓库，八百七十二份 SQL，其中七百三十九份带建表语句，Doris 逻辑模型和 Flink 湖表各一套。

全量扫下来，命中率是百分之百，没有一份完全无话可说。这里面有两类东西。一类是真实问题，比如有十六份 Doris 脚本里写了 select 星号，有四份文件名和它建的表名对不上，其中一份文件名写着 top3，建出来的表叫 top10。另一类是插件自己的毛病，有十五份 Flink 脚本被判括号不配对，点开一看，是中文注释里写了全角左括号配半角右括号。还有二十四份 Hudi 表被提示没有分区字段，其实人家用 k1 当分区列写得清清楚楚。这三类误报我都改了，也补了回归用例。

这一轮下来我最确定的判断是，一个规则引擎的成熟度，跟它见过多少别人写的 SQL 直接相关。自己的用例再全，也只是自己想象出来的世界。

## 它旁边还站着一个记忆插件

数开插件解决的是流程，另一个问题是知识。为什么这么建表，这个字段当年怎么定的口径，上一个做这张表的人踩过什么坑。这些内容不适合塞进流水线，它们属于知识库。

我把这层接上了真实的 OpenViking 服务。用数开插件那边的检索入口去查，能按业务词召回真实文档，也能按表名精确取回正文。把语料仓库里八张表的结构喂进记忆插件，生成一整套域知识，再发布上去，十二个对象落到了远端，回头用数开插件检索，同一份内容原样回来。

这一层也暴露了一个值得记下来的问题。发布成功的时候，返回值里只有 git 提交信息，没有远端同步结果。只提交到本地和真的推上云端，返回结构一模一样，只有远端出错的时候才会报错。我第一遍就是这么被骗过去的，后来靠回头检索才发现远端根本没收到。

## 边界写清楚，比功能介绍更值钱

这个插件的文档里有一份已知缺口清单，写得比功能列表还长。OceanBase 到现在还没有真跑，镜像的大层拉不下来，单机又要两到四个 G 内存。所有真跑都是单机形态，YARN 和 K8s 上的行为没有验证过。命令族的回执拿不到平台侧的 query_id，证据级别只能标成本地回执，这一点在报告里每次都写着，从来不往高里说。

许可证是 Apache 二点零，仓库里有完整的发布流程和验证记录。你要是只想看看它长什么样，克隆下来跑一遍演示，六阶段会自动走完一遍，全程不依赖任何真实组件。

## 写给谁看

如果你手上有一堆靠人盯着的数仓任务，每次上线都要问一遍这个字段对不对，那张表发布了没有，这次改动有没有测过。这个插件解决的就是这类问题。它不替你写 SQL，它要求你写完之后拿出证据。

我还想留住的东西是流程本身。模型的能力一天一个样，今天写不对的 SQL 明天可能就写对了。但一个团队愿不愿意为一次上线留下证据，这件事跟模型没关系。门立在那里，谁来都得走。
