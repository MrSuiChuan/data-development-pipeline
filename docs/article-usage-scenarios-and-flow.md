# 一句需求变成一张上线的表，中间要过哪几道门

上周我拿一句真实需求试了一遍整套流程。需求只有一行，需要统计每日销量 top3 的产品。

插件没有立刻写 SQL。它先把这句话变成一个工单，判断需求属于哪一档，再按档位决定要跑几道门。

这篇讲两件事，它适合接什么样的活，以及接到活以后一步一步怎么走。后面还有一段我被门拦下来的记录，那段比正面介绍更能说明这套东西的边界在哪。

## 先看它接什么活

纯取数不进这条流水线。有人只要一个数，或者一张临时对账的明细，插件有一条 L0 出口，直接给出可执行的查询就结束，不建表、不留交付物。这条出口留着，是因为把取数任务塞进六阶段流程，代价比收益大。

会上生产的那类活才是它要管的。按改动范围分四档。L1 是改造快线，改现有任务、加列、改值，影响面清楚，通常一两天的事。L2 是多表或者涉及中间层的改动，口径要先谈清楚。L3 是新建应用，或者跨好几层的长链路。

定级不走过场。它决定后面跑哪几道门，也决定要不要出架构文档、要不要画链路图、要不要进语义层登记。定级发生在 P1，依据是知识库里的来源表和口径，不是拍脑袋。

难度之外还有一层场景叠加，这两件事不冲突。需求如果落在公共明细层建模、特征标签、或者指标报表上，插件会挂上对应的规范。最典型的是指标类需求，必须在 P6 把口径登记进语义层，不许在 ADS 层随手写一个数就交差。

判断完档位，接下来的动作也分两种。整条流程适合一次做完一整套改动；只想改一张表、补一个用例、看一眼状态，可以走单动作入口，不必为了小改把六个阶段跑一遍。

## 开工前先过准入门

进入研发态要先过五步，工单存在、SDS 终版锚点在工单上、贴单内容重验通过、口径指纹一致、上下文重建。任何一步不过都拒绝开工。

这里有个设计我当初想了很久。P1 的数据概要设计不放在主流程里，它是独立的一步。想清楚和动手做要分开，因为出问题大多出在没想清楚就动手，而模型又特别擅长在没想清楚的时候把话说顺。

设计结论贴在工单评论上，成为跨会话的契约。换个人接手，或者隔一周回来接着做，看到的都是当初谈定的那份口径，不用靠记忆。

## 六个阶段各自产出什么

P1 数据概要设计。产出设计文件加一组验证 SQL。硬规则八条，逐条查目标表、字段映射、结论、可追溯性、分层、证据阈值、知识缺口、增量沉淀。每条映射都要给结论，准确的、不准确的、或者现在还判不了的。判不了的不许进终版，转成知识缺口去问人。三道门也在这里，知识缺口复核门、增量沉淀门、确认门。

我那次的结果是六条字段映射全部准确，三条验证查询真跑过，命中率 1.0，空值率 0，目标表三行。

P2 架构设计。产出架构文档和链路图。文档里必须有一段能机器读的表清单，它后面是 P3 的契约。P3 造出来的表要跟这份清单完全相等，多造少造都拦。中途想加表，回 P2 改清单，不许在 P3 里偷偷加。

这一条看着死板，实际省事。我曾经在一个项目上遇到过设计里三张表、交付出去五张表的情况，多出来的两张半年后没人认领。清单对不上就拦，比事后追认便宜。

P3 数据研发。每张表按 DDL、ETL、任务脚本三层写，顺序不能乱。每份 SQL 过十七项检查，其中九条零容忍。写完要在开发环境真跑一遍，回执由引擎记进执行账本，人不许代写。这一层工程量最大，也是我最经常被拦的地方。

P4 数据测试。产出测试计划和机器记录。规则很硬，报告里打勾的用例，必须在记录里找得到同名的成功结果和 query_id。只想写报告不实跑的，在这道门过不去。

那次四条用例全过，每条都有自己的 query_id，都能回执行账本里查到。

P5 部署。先写部署计划，九条规则，动作限定在建表、改表、回刷、发布质量规则四类。非生产环境直接执行并留证据。生产环境有三道不可逆门，发布、改表、历史回刷各自单独确认，命令里还要带确认过的标记。计划里建议写上回滚脚本，真要回退时不用现想。

P6 语义层。这一步不由 AI 自己决定。先出建议书，人拍板以后才登记。不需要进语义层的项目，这里只做交付登记，然后收尾。

从工单到最后收尾，我那次跑出来是一张 ADS 层的表，三行结果，第一名是 527 号商品，二十件，七千一百二十五块两毛六。

## 门靠什么拦人

门要拦得住，靠的是证据不在模型手里。

真跑的回执、测试的结果、部署的记录，都由引擎自己记。模型写不了，也改不了。出口门要的 query_id 必须能在账本里查到，查不到就是没跑过。这条设计是有意为之，因为让模型自述跑过了，等于没有门。

第二样是内容指纹。设计文件、SQL 脚本、贴单内容各自算一份指纹，改了一个字节，后面的门就会发现证据跟当前脚本对不上。我那次就是靠它发现自己覆盖了执行回执。

第三样是表清单。设计与交付两边做集合比对，多一张少一张都算不一致。

这三样加起来，门拦的是"你到底做没做、做的是不是这一份"，跟模型的态度无关。

## 这些门真的拦过我

讲门控容易被当成文档里的漂亮话，所以我把自己被拦的几次记下来。

第一次是 P3 出口。我在设计里写的目标表带库名，交付表清单里是裸表名，两边指的是同一张表，精确字符串比对把我拦下了。这个拦法过了头，但它说明门是活的，不是摆设。

第二次是 P4 到 P5。我在 P4 用带证据的方式跑了四条测试用例，结果把 P3 的真跑回执覆盖掉了，出口报证据与当前脚本不一致。提示语写的是改了代码就要重跑，可代码一个字没动。定位到根因以后，我把证据按语句类型分开放，只读查询不再占用执行回执。

还有几次是提示语不够用。锚点少写一个版本号，回读校验只回一个失败，不告诉你是锚点的问题。这类问题最后都改成了当场说清楚原因。

两次真拦和几次提示之后，我一共改了六处，每处都补了回归用例。改完要把仓库里的单元测试全跑一遍，一条都不能挂。

## 怎么开始用

开头几条命令就够。先 setup 建运行时，再 submit 建单，然后做概要设计，最后 start 进流水线。

单动作走另外两个入口，改一张表或者看一眼状态用它们。跨会话续接用 resume，它按状态文件把上一次的进度接回来。

配套的东西要另建。插件管流程和门控，来源表长什么样、口径怎么定，来自知识库；真跑要有一个能连上的引擎，离线这边通常是数仓或数据库。我为了让它在真实数据上过一遍，把一套电商数仓的开发库在本地建了出来，一百二十七张表，灌进去以后从 ODS 逐层跑到 ADS，从零重建只要一条命令，重跑得到的结果完全一致。

如果装在一个已经有历史包袱的项目里，我的建议是从单动作入口用起。先用它改一张表、补一个用例，看看门控拦下来的东西有没有价值。觉得有用再往整条流水线上走，不必第一天就把六个阶段全开起来。

## 我的判断

这套流程适合还在靠人盯着的团队。每次上线都要问一遍这个字段对不对、这张表发布了没有、这次改动测过没有，这些问题它替你问。

代价是慢。一个本来半小时能写完的取数需求，走完整流程要花几个小时。所以我把它设计成可以只用一部分，L0 出口和单动作入口就是给这种情况留的。

门控拦得住流程，拦不住判断。口径谈错了，八条硬规则查不出来。它们能保证你要做的那件事被完整想清楚、被真跑验证过、被记录在案，可内容本身对不对，仍然要靠人。
