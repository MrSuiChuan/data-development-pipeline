# 术语表

只解释**本仓库有特定含义**的词。通用词不在这里凑数。

| 术语 | 含义 | 别混淆 |
| --- | --- | --- |
| **工单（ticket）** | 一次数据需求的载体：从建单到交付的全部产物挂在它下面 | 不是"任务"：任务是工单在某阶段的执行单元 |
| **六阶段** | P1 SDS → P2 架构设计 → P3 数据研发 → P4 数据测试 → P5 运维部署 → P6 语义层更新 | 不是"流程建议"：每段都有出口硬门，不过不放行 |
| **出口门（stage_gate）** | 阶段出口的机器检查，只认证据不认自述；不过就返回 FAIL 并说明原因 | 与"软提醒"不同：提醒是自然语言，硬门是返回码与检查键 |
| **SDS（数据概要设计）** | P1 的交付物：`sds_design.json` + `verification/` + 工单终版贴单 | 不是"需求文档"：它必须能被机器核验（八条硬规则） |
| **八条硬规则** | SDS 阶段的准入判据（目标表/来源/口径/验收/风险等必须写实） | 不是"写作要求"：违反即 HALTED |
| **难度定级（L0–L3）** | P1 导出 `level`，决定后续走哪条路径：L0 即席出口 / L1 改造快线 / L2 待明确慢线 / L3 新建应用 | 不是"工作量估计"：它决定门控的严格度（L2≥15 用例、L3≥25 用例等） |
| **SQL 17 项检查** | P3 对交付 SQL 的静态检查清单 | 不是"风格检查"：它拦的是会算出错数据的写法 |
| **证据绑定（sql_hash）** | 阶段证据要绑定到它验证的那份 SQL：SQL 改了，旧证据立刻失效 | 不是"跑过就行"：跑过的那一份 ≠ 你正要发布的这一份 |
| **机器资产** | `.data-dev/` 下由引擎写、不允许手改的东西：`_state.json`、`runtime/**`、审计与账本 | 手改会被 hook 拦；改了等于伪造留证 |
| **留证** | 可复核的原始依据：`etl_dev_exec.json`、`test_runs.json`、`deploy_log.json`、账本里的 query_id | 不是"日志"：留证要能被门消费，只写不读的不算证据 |
| **连接器 / 方言** | `engine/core/clients.py` 与 `dialects.py`：把平台命令与 SQL 方言抽象掉，让仓库里不带平台专有名 | 不是"驱动"：本仓库不打包任何第三方驱动或二进制 |
| **DQC** | 数据质量布防（规则与产出物） | 不是"测试"：DQC 是上线后长期生效的约束，P4 是一次性验证 |
| **回刷（backfill）** | 用受控范围重跑历史分区 | 不是"重跑任务"：回刷有范围门与顺序纪律，禁 SUPPLEMENT 那类绕行 |
| **CDM** | 公共维度/明细中间层，强调复用性与命名规范 | 不是"随便抽一层"：它的价值在于被多处复用 |
| **语义层** | 指标与口径的对外登记（P6）；口径变更要走语义层更新而不是改 SQL | 不是"文档"：它是对外承诺，改了要有拍板 |
| **autopilot** | 全托管跑完 P1–P6 的模式 | 不是"无人值守"：三道不可逆门（发布/ALTER/回刷）仍要当次确认原话 |

## 常见误解

- **"装了插件就有数据平台了"**：不是。它是工艺与门控；平台命令、MCP 服务名、内部代号
  全部通过项目级配置注入，仓库里不带。
- **"门控通过了就是做对了"**：门控只保证"该有的证据齐全且对得上"，不保证业务口径正确——
  口径要靠 SDS 与语义层上的人来拍。
- **"hook 是安全边界"**：不是。它让偷懒变贵；真正拦事的是引擎内的门与证据比对。
- **"测试数量写在 README 里方便"**：本仓库禁止——面向用户的文档写死数量必然与实际漂移
  （`tests/test_oss_readiness.py` 会拦）。
